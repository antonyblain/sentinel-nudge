## Leçons

| LL-001 | 2026-04-11 | Processus | Production de 3 fichiers distincts pour un même livrable (draft, v1.0, compléments) au lieu de maintenir un seul document | La grille d'analyse uniforme et la rigueur scientifique | La multiplication des fichiers a créé de la confusion pour le Commanditaire | Règle : mettre à jour le document en place pour des modifications mineures, ou incrémenter la version majeure et supprimer l'ancienne version. | LL-002 | 2026-04-11 | Technique | Tentative de lecture d'un fichier de 24468 tokens (CdC v1.0, ~1500 lignes) sans offset/limit, provoquant une erreur de dépassement du seuil de 10000 tokens | Le fallback avec offset+limit par blocs de 200 lignes a fonctionné | La première tentative en lecture intégrale a échoué et gaspillé un appel outil | **Règle permanente** : tout fichier susceptible de dépasser 200 lignes doit être lu par blocs (offset+limit de 200 lignes max) ou via Grep ciblé sur les sections pertinentes. Avant de lire un fichier volumineux, estimer sa taille ou utiliser Grep pour localiser la section d'intérêt. |
| LL-003 | 2026-04-11 | Git | Tentative de commit sur un nouveau poste sans vérifier la configuration Git (user.name/user.email absents) | L'erreur a été identifiée rapidement grâce au message Git explicite | Le commit a échoué, nécessitant une action manuelle du Commanditaire et un second passage | **Règle permanente** : avant tout commit prescrit au Commanditaire ou exécuté par l'assistant, vérifier `git config user.name` et `git config user.email`. Si absent, prescrire la configuration en premier. Particulièrement important lors d'un changement de poste ou d'un premier checkout. |
| LL-004 | 2026-04-11 | Git | Commande `git add` construite à partir d'un état supposé des fichiers (ancien nom v1.0) alors que le fichier avait déjà été renommé en v1.1 | Le diagnostic de l'erreur pathspec a été rapide | L'erreur a gaspillé un appel et aurait pu être évitée | **Règle permanente** : toujours relire `git status` juste avant de construire les commandes git add/rm/commit. Ne jamais se fier à un état supposé — un fichier peut avoir été renommé, supprimé ou modifié entre-temps. |
| LL-005 | 2026-04-11 | Processus | Modification du SFD (ajout passphrase M9) sans penser à mettre à jour les fichiers .mmd sources et les images PNG. Le Commanditaire a dû signaler l'oubli. | La correction a été rapide une fois identifiée | La chaîne de documents dérivés n'a pas été suivie, créant une incohérence temporaire entre le SFD, les sources Mermaid et les images | **Règle permanente — Chaîne de modification documentaire** : toute modification du SFD qui touche un diagramme impose la mise à jour de toute la chaîne : (1) bloc Mermaid dans le .md, (2) fichier .mmd dans sources/, (3) PNG régénéré dans images/. Plus largement, avant de commiter une modification, toujours se poser la question : « quels autres fichiers sont dérivés de ou liés à ce que je viens de modifier ? » (matrice de traçabilité, compteurs CA, SESSION.md, BACKLOG.md). |
| LL-006 | 2026-04-11 | Processus | Le comité d'architecture P3 a produit 15 corrections (schéma password_hashes, domain_hash salé, périmètre chiffrement, rôles ARIA, etc.) qui modifient directement le SFD. Le DAT v1.1 a été produit avec les corrections, mais le SFD n'a PAS été mis à jour en v1.1. Le référent qualité a dû signaler 3 incohérences bloquantes lors de la revue globale. | Le référent qualité a bien détecté les incohérences lors de la revue de 2nd niveau | La rétro-propagation des décisions de comité vers les documents amont n'a pas été faite. Le SFD et le DAT décrivaient des schémas différents pour la même implémentation. | **Règle permanente — Rétro-propagation post-comité** : immédiatement après la rédaction du PV d'un comité, vérifier si les décisions prises modifient des spécifications de documents antérieurs (SFD, CdC). Si oui, mettre à jour ces documents AVANT de passer à la soumission. Ne jamais attendre la revue qualité pour détecter ces incohérences — c'est un échec de processus. Checklist : SFD impacté ? CdC impacté ? Diagrammes impactés ? RISQUES/BACKLOG/TECH_STACK impactés ? |
| LL-007 | 2026-04-11 | Technique | 9 anomalies rencontrées lors de l'initialisation du socle P4 : versions npm incorrectes dans le DAT (vite-plugin-web-extension ^0.13 n'existe pas → v4.5, @typescript-eslint ^7 incompatible ESLint 9 → ^8), format ESLint obsolète (.eslintrc.json → eslint.config.js flat config), HTML référençant .js au lieu de .ts (Vite exige .ts), root Vite manquant (src/), manifest avec .js au lieu de .ts, jsdom manquant, SubtleCrypto non dispo dans jsdom, package.json sans type:module. | Le diagnostic de chaque erreur a été rapide grâce aux messages d'erreur explicites | **Les versions documentées dans le DAT n'avaient pas été vérifiées contre npm.** Aucun `npm view <pkg> versions` n'a été exécuté en P3 pour confirmer l'existence des versions prescrites. | **Règle permanente — Vérification des versions npm en P3** : avant de figer une version dans le DAT (Annexe A), toujours exécuter `npm view <pkg> versions` pour confirmer que la version existe sur le registre npm. Vérifier aussi les peer dependencies entre les packages (ex: ESLint 9 exige @typescript-eslint ^8). Après la phase de développement P4, toujours faire un PDCA pour corriger les docs si les versions réelles diffèrent. |

| LL-008 | 2026-04-12 | Technique | Les 7 composants UI (overlays, toasts) utilisaient customElements.define() pour s'enregistrer comme Web Components. En content script Chrome MV3, customElements.define() s'exécute dans l'isolated world mais document.createElement() crée un HTMLUnknownElement. new Class() lance "Illegal constructor". Le toast M17 et l'indicateur M9 étaient invisibles/crashants. | La construction DOM directe (createElement + attachShadow + styles inline) fonctionne parfaitement. | 5 tentatives successives (registerXxx, window.customElements, try-catch, new Class) avant de comprendre que les Custom Elements sont fondamentalement incompatibles avec les content scripts MV3. | **Règle permanente** — pour les content scripts Chrome MV3, toujours construire les composants UI via createElement + attachShadow. Ne jamais utiliser customElements.define(). |
