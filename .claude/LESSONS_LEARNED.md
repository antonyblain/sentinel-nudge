| LL-022 | 2026-04-17 | Processus | Parallélisation intensive d'agents Fabrique (jusqu'à 3 simultanés) sur une session de 90 min : 7 PR mergées via délégation en agents background avec isolation worktree. Forte accélération mais 3 incidents mineurs : (1) agents qui écrivent initialement dans le repo principal au lieu du worktree isolé — T-075 puis T-110 signalés l'incident avant correction (leçon à capitaliser dans les briefs), (2) collision potentielle sur `.claude/BACKLOG.md` si plusieurs agents y ajoutent des tâches en parallèle — résolu en centralisant l'ajout dans une seule PR, (3) difficulté à choisir entre "1 grosse PR combinée" vs "N petites PR parallèles" selon les zones touchées. | La parallélisation multiplie le throughput de 3× à 5× sur des tâches de même pattern (ex. chantier A audit ADR — M2 fait seul, M3+M5+M6 combinés). Les worktrees isolés `.claude/worktrees/agent-<id>` permettent des branches git parallèles sans collision de HEAD. | Sans vigilance sur les briefs (rappel `pwd` obligatoire avant Write) et le cleanup post-merge (worktrees + branches orphelines), le repo s'enlise en pollution git. Les zones partagées (`.claude/BACKLOG.md`, `src/shared/types/diagnostics.ts`) sont des points chauds de conflit si non centralisées. | **Pattern permanent — Parallélisation agents Fabrique** : (1) limiter à **2 agents simultanés max** en worktrees (au-delà l'isolation devient fragile), (2) imposer dans chaque brief : « vérifier `pwd` avant tout Write, CWD attendu `/c/Dev/sentinel-nudge/.claude/worktrees/agent-<id>` », (3) segmenter strictement les **zones autorisées** par agent (périmètre explicite), (4) pour des tâches de même pattern (ex. chantier A M3/M5/M6), préférer **1 agent combiné** plutôt que 3 parallèles, (5) centraliser toute modification de fichier partagé (`.claude/BACKLOG.md`, `docs/securite/referentiel-*.md`) dans **un seul agent à la fois**. |

| LL-023 | 2026-04-17 | Processus | Lors d'une session avec plusieurs agents Fabrique en background, la notification de complétion d'un agent peut arriver avec un retard significatif (observé +18 min sur T-114). Pendant ce temps, la PR est ouverte, CI verte, mais n'est pas mergée — le flux est bloqué. Le Commanditaire a détecté le problème visuellement avant que l'orchestrateur ne le voie. | Les notifications `task-notification` du runtime sont fiables à terme mais pas temps-réel. | S'appuyer uniquement sur les notifications automatiques = attente passive = latence perçue par le Commanditaire. | **Règle permanente — Check pro-actif agents background** : après avoir lancé 1+ agent en background, mettre en place un **Monitor dédié** qui scanne `gh pr list --state open --author @me` toutes les 60-120s, ou faire un check manuel `gh pr list` + `gh run list` toutes les 10-15 min pendant l'attente. Ne jamais supposer que l'absence de notification = agent toujours en cours. Cette règle est à appliquer **même quand un Monitor existe déjà** sur une autre PR (les Monitors ne sont pas transférables). |

| LL-024 | 2026-04-17 | Git | Après merge d'une PR issue d'un agent Fabrique avec `gh pr merge --delete-branch`, le worktree local `.claude/worktrees/agent-<id>` et la branche locale `worktree-agent-<id>` ne sont pas supprimés automatiquement. Accumulation progressive jusqu'à 4+ worktrees orphelins, bloquant les futurs `--delete-branch`. | `git worktree remove -f -f` permet de forcer le cleanup même quand le worktree est locked par le runtime. | Pas de cleanup automatique dans le cycle agent → PR → merge. Les artefacts git s'accumulent. | **Routine post-merge permanente** : après chaque `gh pr merge --delete-branch` d'une PR issue d'un agent Fabrique, exécuter en chaîne : `git worktree remove -f -f .claude/worktrees/agent-<id>` + `git branch --delete --force worktree-agent-<id>`. À défaut, batch périodique en fin de session : `git worktree list` pour identifier les worktrees pointant sur une branche mergée (ou absente de `origin`), puis cleanup groupé. |
